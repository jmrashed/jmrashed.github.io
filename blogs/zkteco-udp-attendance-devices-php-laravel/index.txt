25:T56a6,<p class="blog-p">Fingerprint, face and RFID attendance devices keep their punch logs inside the box. A web application that wants to read those punches, enrol a user or sync the clock needs a way to reach the device directly, over the network, without a separate desktop program in the middle. That is what I built <a href="https://github.com/jmrashed/zkteco" target="_blank" rel="noopener">jmrashed/zkteco</a> for: an open-source PHP package, usable from Laravel, that talks to these devices over UDP. The repository was created in April 2024.</p>

<p class="blog-p">As of 22 November 2026, <a href="https://packagist.org/packages/jmrashed/zkteco" target="_blank" rel="noopener">Packagist</a> shows 28,534 total downloads (about 4,500 a month), and the GitHub repository has 69 stars and 25 forks. Downloads are not installs and stars are not production usage, so I treat those numbers as a sign that other people hit the same wall, not as proof of anything more. What I care about more is what the package taught me about talking to hardware. This post walks through how the protocol client works, using the actual source, and ends with the bugs that real devices forced me to fix.</p>

<blockquote class="blog-blockquote">Scope note: everything below describes the package's code at commit <code class="blog-code-inline">4fd2ac2</code>. I did not write the device protocol; the source itself says its checksum and time helpers were copied from the vendor's reference C code (<code class="blog-code-inline">zkemsdk.c</code>). Device firmware varies, so treat the byte layouts as "what this parser reads", not as a specification.</blockquote>

<h2 class="blog-h2">1. The transport: plain UDP from PHP</h2>

<p class="blog-p">The device speaks a binary protocol over <a href="https://www.rfc-editor.org/rfc/rfc768" target="_blank" rel="noopener">UDP</a>, by default on port 4370. PHP can do this with nothing but its <a href="https://www.php.net/manual/en/book.sockets.php" target="_blank" rel="noopener">sockets extension</a>, which is why the package has no Laravel dependency in its core and the README's first setup step is enabling <code class="blog-code-inline">extension=sockets</code>.</p>

<p class="blog-p">The constructor creates a datagram socket and sets a receive timeout of 60.5 seconds. That is a generous default, and it is a trade-off worth knowing about: UDP gives you no connection error when the other end is unreachable, busy or asleep, so you find out only by waiting for the timeout.</p>

<pre class="blog-pre"><code class="blog-code-block">$this-&gt;_zkclient = socket_create(AF_INET, SOCK_DGRAM, SOL_UDP);
$timeout = ['sec' =&gt; 60, 'usec' =&gt; 500000];
socket_set_option($this-&gt;_zkclient, SOL_SOCKET, SO_RCVTIMEO, $timeout);</code></pre>

<p class="blog-p">The first design consequence of UDP is that nothing is guaranteed: a datagram can be lost, duplicated or arrive out of order. The protocol compensates with a session id and a reply counter in every packet, which is the next piece.</p>

<h2 class="blog-h2">2. Anatomy of a packet</h2>

<p class="blog-p">Every message, in both directions, is an 8-byte header followed by an optional payload. The header is four unsigned 16-bit integers:</p>

<table class="blog-table">
<thead class="blog-thead"><tr class="blog-tr"><th class="blog-th">Field</th><th class="blog-th">Size</th><th class="blog-th">Purpose</th></tr></thead>
<tbody class="blog-tbody">
<tr class="blog-tr"><td class="blog-td">command</td><td class="blog-td">2 bytes</td><td class="blog-td">What to do, e.g. 1000 connect, 13 read attendance log, 2000 acknowledge</td></tr>
<tr class="blog-tr"><td class="blog-td">checksum</td><td class="blog-td">2 bytes</td><td class="blog-td">Integrity check over the whole packet</td></tr>
<tr class="blog-tr"><td class="blog-td">session id</td><td class="blog-td">2 bytes</td><td class="blog-td">Issued by the device on connect; echoed on every later command</td></tr>
<tr class="blog-tr"><td class="blog-td">reply id</td><td class="blog-td">2 bytes</td><td class="blog-td">A counter that increases with every command and wraps at 65535</td></tr>
</tbody>
</table>

<p class="blog-p">The library builds this with PHP's <a href="https://www.php.net/manual/en/function.pack.php" target="_blank" rel="noopener">pack()</a>. The one subtle point is that it uses the <code class="blog-code-inline">S</code> format, which is the machine's own byte order. That is little-endian on the x86 and ARM servers PHP normally runs on, which is what the device expects, but it is a portability assumption worth knowing about.</p>

<pre class="blog-pre"><code class="blog-code-block">static public function createHeader($command, $chksum, $session_id, $reply_id, $command_string)
{
    $buf = pack('SSSS', $command, $chksum, $session_id, $reply_id) . $command_string;
    $buf = unpack('C' . (8 + strlen($command_string)) . 'c', $buf);

    $chksum = unpack('S', self::createChkSum($buf))[1];

    $reply_id += 1;
    if ($reply_id &gt;= self::USHRT_MAX) {
        $reply_id -= self::USHRT_MAX;
    }

    return pack('SSSS', $command, $chksum, $session_id, $reply_id) . $command_string;
}</code></pre>

<p class="blog-p">The checksum treats the packet as a sequence of 16-bit words, adds them up, folds any overflow back into 16 bits, adds a trailing odd byte if there is one, then negates the result and subtracts one. It resembles the classic internet checksum with a vendor-specific twist, which is why the code copies the vendor's routine instead of reinventing it. With a binary protocol over UDP, a wrong checksum is the kind of mistake that is hard to diagnose, because the usual symptom is no reply at all. Test your packet builder against known-good packets before anything else.</p>

<h2 class="blog-h2">3. The handshake and the session</h2>

<p class="blog-p">A conversation starts with command 1000 (connect), sent with session id 0 and a reply id of 65534. The device answers with an acknowledgement whose header carries the session id it has assigned to you. The library reads bytes 4 and 5 of the reply, stores that number, and sends it with every command afterwards. An empty session id means the connect failed, even if some bytes came back.</p>

<pre class="blog-pre"><code class="blog-code-block">$command = Util::CMD_CONNECT;      // 1000
$session_id = 0;
$reply_id = -1 + Util::USHRT_MAX;  // 65534

$buf = Util::createHeader($command, 0, $session_id, $reply_id, '');
socket_sendto($self-&gt;_zkclient, $buf, strlen($buf), 0, $self-&gt;_ip, $self-&gt;_port);
@socket_recvfrom($self-&gt;_zkclient, $self-&gt;_data_recv, 1024, 0, $self-&gt;_ip, $self-&gt;_port);

// session id = bytes 4-5 of the reply, little-endian
$session = hexdec($u['h6'] . $u['h5']);</code></pre>

<p class="blog-p">One honest limitation lives in <code class="blog-code-inline">checkValid()</code>. It accepts both 2000 (acknowledge OK) and 2005 (connection unauthorized) as success, with a <code class="blog-code-inline">TODO</code> comment saying so. Some devices answer the connect with "unauthorized" when a communication password is set, and the library currently does not handle that authentication step. If your device has a comm key, this is where you will hit trouble.</p>

<h2 class="blog-h2">4. Bulk data: a stream hidden inside datagrams</h2>

<p class="blog-p">Small commands, such as reading the firmware version, get a single reply. The attendance log does not. When you send command 13 (read attendance log), the device does not reply with the data. It replies with command 1500 (<code class="blog-code-inline">CMD_PREPARE_DATA</code>) whose payload is the total number of bytes it is about to send, and then it streams the data in datagrams of up to 1,032 bytes. The client's job is to keep reading until it has collected that many bytes.</p>

<pre class="blog-pre"><code class="blog-code-block">$bytes = self::getSize($self);   // total size announced by CMD_PREPARE_DATA
$received = 0; $errors = 0;

while ($bytes &gt; $received) {
    $ret = @socket_recvfrom($self-&gt;_zkclient, $dataRec, 1032, 0, $self-&gt;_ip, $self-&gt;_port);
    if ($ret === false) {
        if ($errors &lt; $maxErrors) { $errors++; sleep(1); continue; }
        return '';               // give up after 10 failed reads
    }
    $data .= $dataRec;
    $received += strlen($dataRec);
}
// flush whatever trailing packet is left on the socket
@socket_recvfrom($self-&gt;_zkclient, $dataRec, 1024, 0, $self-&gt;_ip, $self-&gt;_port);</code></pre>

<p class="blog-p">Two details matter here. First, a failed read is retried up to ten times with a one-second pause, because on a flaky network a missing datagram often means "slow", not "lost". Second, the trailing flush: the library reads and discards one more datagram after the data is complete, so a leftover packet cannot be mistaken for the reply to the next command. On a socket shared across many commands, a stray datagram left in the buffer makes every later reply one step out of line, which is a nasty class of bug to track down.</p>

<h3 class="blog-h3">Parsing the records</h3>

<p class="blog-p">Once the bytes are in, the parser skips the first 10 and walks the rest in 40-byte records. Reading the offsets in the current code, the fields it extracts are:</p>

<table class="blog-table">
<thead class="blog-thead"><tr class="blog-tr"><th class="blog-th">Field</th><th class="blog-th">Where the parser reads it</th><th class="blog-th">Notes</th></tr></thead>
<tbody class="blog-tbody">
<tr class="blog-tr"><td class="blog-td">uid</td><td class="blog-td">bytes 2-3 of the record</td><td class="blog-td">Little-endian 16-bit internal user number</td></tr>
<tr class="blog-tr"><td class="blog-td">id</td><td class="blog-td">bytes 4-12</td><td class="blog-td">Badge or user id, null-padded text</td></tr>
<tr class="blog-tr"><td class="blog-td">state</td><td class="blog-td">byte 28</td><td class="blog-td">0 password, 1 fingerprint, 2 card</td></tr>
<tr class="blog-tr"><td class="blog-td">timestamp</td><td class="blog-td">bytes 29-32</td><td class="blog-td">Little-endian, decoded with the time routine below</td></tr>
<tr class="blog-tr"><td class="blog-td">type</td><td class="blog-td">byte 33</td><td class="blog-td">0 check-in, 1 check-out, 4 overtime-in, 5 overtime-out</td></tr>
</tbody>
</table>

<p class="blog-p">These offsets are the weak point of the whole library. They are read out of a hex string by position, and they fit the devices the package was developed against. Some other devices send the data differently, and the README lists "known device-specific parsing caveats". That is exactly what <a href="https://github.com/jmrashed/zkteco/issues/7" target="_blank" rel="noopener">issue #7</a> ("Incorrect attendance data parsing id and timestamp") describes, and it is still open. The package's answer so far is an opt-in <code class="blog-code-inline">getSanitizedAttendance()</code> that drops records failing basic sanity checks. It is deliberately opt-in so it cannot silently discard legitimate punches on devices that already parse correctly. The real fix needs raw packet captures from the affected devices.</p>

<h2 class="blog-h2">5. The time format that is not a Unix timestamp</h2>

<p class="blog-p">The device stores time as one integer, but not seconds since 1970. The formula, taken from the vendor reference code, packs the date as if every month had 31 days:</p>

<pre class="blog-pre"><code class="blog-code-block">$d = (($year % 100) * 12 * 31 + (($month - 1) * 31) + $day - 1) * 86400
   + ($hour * 60 + $minute) * 60 + $second;</code></pre>

<p class="blog-p">For 22 November 2026 at 10:00:00 that gives (26 x 372 + 10 x 31 + 21) x 86400 + 36000 = 864,295,200. Decoding reverses it with repeated division by 60, 60, 24, 31 and 12, then adds 2000 to the year. Two practical consequences follow. First, you cannot compare these raw numbers to Unix time or do date arithmetic on them. You must decode first. Second, the value carries no timezone. The package returns the device's wall-clock time as a string, which means a device whose clock is wrong, or set to a different zone than your server, produces records that look fine and are quietly off. Syncing the device clock with <code class="blog-code-inline">setTime()</code> is the first thing I would do on any new installation.</p>

<h2 class="blog-h2">6. Writing to the device: when a payload does not fit in one packet</h2>

<p class="blog-p">Reading is the simpler half. Writing a fingerprint template to a device failed on real templates because templates are commonly 500 to 1,500 bytes or more, and the first version of the library sent the whole thing in a single UDP packet. Real templates simply did not arrive intact (<a href="https://github.com/jmrashed/zkteco/issues/6" target="_blank" rel="noopener">issue #6</a>, <a href="https://github.com/jmrashed/zkteco/issues/11" target="_blank" rel="noopener">issue #11</a>). The device has its own chunked upload protocol, the mirror image of the download one: announce the size, send the data in chunks, then issue the real command.</p>

<pre class="blog-pre"><code class="blog-code-block">static public function sendWithBuffer(ZKTeco $self, $command, $data)
{
    if (strlen($data) &lt;= self::MAX_CHUNK_SIZE) {          // 1024 bytes
        return $self-&gt;_command($command, $data);
    }

    $prepared = $self-&gt;_command(self::CMD_PREPARE_DATA, pack('V', strlen($data)));
    if ($prepared === false) { return false; }

    foreach (str_split($data, self::MAX_CHUNK_SIZE) as $chunk) {
        if ($self-&gt;_command(self::CMD_DATA, $chunk) === false) { return false; }
    }

    return $self-&gt;_command($command, '');                 // e.g. CMD_USER_TEMP_WRQ
}</code></pre>

<p class="blog-p">The fix shipped in version 2.1.0. Small payloads still take the original direct path, so existing behaviour did not change. There is a test for it (<code class="blog-code-inline">SendWithBufferTest</code>), and the lesson I took from it is general: any protocol that runs over datagrams has a size limit somewhere, and you only discover it when the first realistic payload exceeds it.</p>

<h2 class="blog-h2">7. What real devices taught me</h2>

<p class="blog-p">The 2.1.0 changelog is a good record of what only real devices and real users exposed. Each item below links to the original report.</p>

<ul class="blog-ul">
<li class="blog-li"><strong class="blog-strong">Short or empty replies crash the parser.</strong> After a failed connect, the response was empty and <code class="blog-code-inline">unpack()</code> threw "Type H: not enough input" (<a href="https://github.com/jmrashed/zkteco/issues/2" target="_blank" rel="noopener">#2</a>). The fix was a guard: check the length before unpacking. There is a dedicated test, <code class="blog-code-inline">ShortDataGuardTest</code>, so it cannot regress.</li>
<li class="blog-li"><strong class="blog-strong">A static/instance mismatch.</strong> <code class="blog-code-inline">getTodaysRecords()</code> was fatal when called the documented way (<a href="https://github.com/jmrashed/zkteco/issues/3" target="_blank" rel="noopener">#3</a>). A reminder that README examples deserve tests too.</li>
<li class="blog-li"><strong class="blog-strong">A limit that did not limit.</strong> <code class="blog-code-inline">getAttendanceWithLimit($limit)</code> ignored its argument (<a href="https://github.com/jmrashed/zkteco/issues/5" target="_blank" rel="noopener">#5</a>, titled "slow"). It now honours the limit, but be clear about what that means: the protocol has no "give me the last N" command, so the library still downloads the whole log and slices it afterwards. <code class="blog-code-inline">getAttendanceByDateRange()</code> works the same way. On a device with a year of punches, that is still a large transfer.</li>
<li class="blog-li"><strong class="blog-strong">Disable the device while you talk to it.</strong> The README says to call <code class="blog-code-inline">disableDevice()</code> before reading or writing and <code class="blog-code-inline">enableDevice()</code> afterwards. Per the comments in <code class="blog-code-inline">Util.php</code>, the disable command puts the device into a "shut-down" condition that shows an in-progress message on its screen, so if you skip <code class="blog-code-inline">enableDevice()</code> the device stays unusable for the people standing at it.</li>
</ul>

<h2 class="blog-h2">8. How I would use it in production</h2>

<p class="blog-p">The minimal flow is short, and the shape of it is the part worth copying:</p>

<pre class="blog-pre"><code class="blog-code-block">composer require jmrashed/zkteco

use Jmrashed\Zkteco\Lib\ZKTeco;

$zk = new ZKTeco('192.168.1.201');      // default port 4370

if ($zk-&gt;connect()) {
    $zk-&gt;disableDevice();
    $log = $zk-&gt;getAttendance();         // uid, id, state, timestamp, type
    $zk-&gt;enableDevice();
    $zk-&gt;disconnect();
}</code></pre>

<p class="blog-p">Around that flow I would add the things a library cannot decide for you:</p>

<ul class="blog-ul">
<li class="blog-li"><strong class="blog-strong">Run it from a queue, not a web request.</strong> With a 60-second receive timeout and a log download that can be large, a request thread is the wrong place for it. A scheduled job that pulls and stores the log is.</li>
<li class="blog-li"><strong class="blog-strong">Keep the device off the public internet.</strong> UDP with a session id and a checksum is an integrity check, not security. Put the device on an isolated network segment that only your application server can reach.</li>
<li class="blog-li"><strong class="blog-strong">Store the raw log, then process it.</strong> Import every record into your own table keyed by uid and timestamp, and make the import idempotent so a retry cannot double-count a punch. Never treat the device as your system of record.</li>
<li class="blog-li"><strong class="blog-strong">Always call enable and disconnect, even on failure.</strong> Put them in a <code class="blog-code-inline">finally</code> block so one exception does not leave the device locked.</li>
</ul>

<h2 class="blog-h2">What I would improve next</h2>

<p class="blog-p">Reading the code again for this post, three weak spots stand out. Record parsing by position in a hex string should become a small reader that is told which device layout to expect, with real packet captures kept as test fixtures. The authentication reply (2005) should be handled properly instead of sitting behind a <code class="blog-code-inline">TODO</code>. And the date-range and limit helpers should say more loudly that they filter after a full download. None of this changes the main lesson: in a protocol client, the happy path is the small part. The network, the firmware variations and the edge cases are the rest of the work.</p>

<p class="blog-p">There is also a sibling project for Node.js, <a href="https://github.com/jmrashed/zk-attendance-sdk" target="_blank" rel="noopener">zk-attendance-sdk</a>, that targets the same devices from TypeScript. If you have a device that parses wrongly, a packet capture attached to <a href="https://github.com/jmrashed/zkteco/issues/7" target="_blank" rel="noopener">issue #7</a> is the most useful contribution anyone can make.</p>
