25:T62c3,<p class="blog-p">Placing an order sounds like one operation: take the money, reserve the stock, create the shipment. Inside one application with one database, a single transaction can cover the database part of that. Give payment, inventory and shipping their own databases and that transaction is gone. <a href="https://github.com/jmrashed/smallest-microservice" target="_blank" rel="noopener">smallest-microservice</a> is my small, readable version of the usual answer, the saga: an order pipeline built from four services in four languages, each with its own MySQL database, talking only through RabbitMQ.</p>

<p class="blog-p">It is small enough to read from end to end, which makes it a useful place to look at what a saga needs in real code: who reacts to what, how a failed step is undone, how a redelivered message is kept from doing the work twice, and which failures are still not handled.</p>

<blockquote class="blog-blockquote">Scope note: everything below comes from reading the repository at commit <code class="blog-code-inline">d8aa267</code>. This is not a report of a test run or a benchmark. The repository describes itself as a learning demo, not production code.</blockquote>

<figure class="blog-figure"><a href="/images/blog/order-saga-flow.svg" target="_blank" rel="noopener"><img class="blog-img" src="/images/blog/order-saga-flow.svg" width="1000" height="900" alt="Sequence diagram of the order saga across the Node.js order, Python payment, Go inventory and PHP shipping services, each with its own database. Node sends q.order_created to Python. A declined payment returns q.payment_failed to Node. An accepted one sends q.payment_completed to Go. If stock is reserved, Go sends q.stock_reserved to PHP, which sends q.shipment_created to Node and the order is fulfilled. If stock is unavailable, Go sends q.stock_unavailable to Python, which refunds and sends q.payment_refunded to Node, and the order is cancelled."></a><figcaption class="blog-figcaption">The full saga and its three endings. <h2 class="blog-h2">1. Four services, four databases</h2>

<table class="blog-table">
<thead class="blog-thead"><tr class="blog-tr"><th class="blog-th">Service</th><th class="blog-th">Language</th><th class="blog-th">Job</th><th class="blog-th">Database</th></tr></thead>
<tbody class="blog-tbody">
<tr class="blog-tr"><td class="blog-td">Order</td><td class="blog-td">Node.js (Express)</td><td class="blog-td">HTTP API, creates orders, records their final status</td><td class="blog-td">orders_db</td></tr>
<tr class="blog-tr"><td class="blog-td">Payment</td><td class="blog-td">Python (pika)</td><td class="blog-td">Accepts or declines a payment, refunds if stock is unavailable</td><td class="blog-td">payments_db</td></tr>
<tr class="blog-tr"><td class="blog-td">Inventory</td><td class="blog-td">Go</td><td class="blog-td">Reserves stock or reports it unavailable</td><td class="blog-td">inventory_db</td></tr>
<tr class="blog-tr"><td class="blog-td">Shipping</td><td class="blog-td">PHP</td><td class="blog-td">Creates the shipment record</td><td class="blog-td">shipping_db</td></tr>
</tbody>
</table>

<p class="blog-p">There is also a small React and Tailwind web UI that places orders and shows what happened to each one. No service reads or writes another service's database. In this repository that is a rule the code follows, not one the infrastructure enforces: all four connect to MySQL with the same local user.</p>

<p class="blog-p">The business rules are deliberately tiny. The payment "charge" is a row in a table, and any amount above 1000 is declined. The stock table is seeded with three products, one of which, <code class="blog-code-inline">OUT_OF_STOCK</code>, has zero units, so you can trigger the compensation path whenever you like. The small rules keep the attention on the messaging.</p>

<h2 class="blog-h2">2. Choreography: nobody is in charge</h2>

<p class="blog-p">A <a href="https://microservices.io/patterns/data/saga.html" target="_blank" rel="noopener">saga</a> replaces one distributed transaction with a sequence of local transactions. Each service commits its own step and announces the result. When a later step fails, earlier steps are not rolled back by the database; the application runs a compensating action instead. There are two common ways to drive the sequence: an orchestrator that tells each participant what to do, or choreography, where each participant reacts to events from the others. This project uses choreography.</p>

<p class="blog-p">So the workflow is not written down in any single file. It is spread across the queues each service subscribes to:</p>

<ul class="blog-ul">
<li class="blog-li"><strong class="blog-strong">Payment declined:</strong> <code class="blog-code-inline">q.order_created</code> goes to Python, then <code class="blog-code-inline">q.payment_failed</code> goes back to Node. The order ends as <code class="blog-code-inline">payment_failed</code>.</li>
<li class="blog-li"><strong class="blog-strong">Happy path:</strong> <code class="blog-code-inline">q.payment_completed</code> goes to Go, <code class="blog-code-inline">q.stock_reserved</code> to PHP, and <code class="blog-code-inline">q.shipment_created</code> to Node. The order ends as <code class="blog-code-inline">fulfilled</code>.</li>
<li class="blog-li"><strong class="blog-strong">Out of stock:</strong> after payment succeeds, Go publishes <code class="blog-code-inline">q.stock_unavailable</code>. Python marks the payment refunded and publishes <code class="blog-code-inline">q.payment_refunded</code>. The order ends as <code class="blog-code-inline">cancelled_out_of_stock</code>.</li>
</ul>

<p class="blog-p">The gain is that no service knows another service's address, and there is no central component to build. The cost is that to answer "what happens after payment?", you have to find who consumes that queue. With four services that is manageable. It gets harder as the number of steps and branches grows, which is the usual argument for an orchestrator.</p>

<h2 class="blog-h2">3. The queue name is the contract</h2>

<p class="blog-p">Messages are published to RabbitMQ's <a href="https://www.rabbitmq.com/tutorials/tutorial-two-python" target="_blank" rel="noopener">default exchange</a> with the queue name as the routing key, so each event lands in one named queue. The body is plain JSON. There is no schema registry and no shared library: the contract between two services is a queue name plus the fields each side expects. Go is the one service that spells those fields out as a type:</p>

<pre class="blog-pre"><code class="blog-code-block">type Message struct {
	OrderID   int     `json:"order_id"`
	ProductID string  `json:"product_id"`
	Quantity  int     `json:"quantity"`
	Amount    float64 `json:"amount"`
	Event     string  `json:"event"`
	CreatedAt string  `json:"created_at"`
}</code></pre>

<p class="blog-p">This has a practical consequence for the API. The payload that starts in Node is passed along by the next services, each adding its own event name and timestamp. If the first message carries a quantity as the string <code class="blog-code-inline">"2"</code>, a strictly typed consumer further down cannot decode it, by which point an earlier step has already committed. That is why <code class="blog-code-inline">POST /orders</code> checks types and ranges before it writes anything: <code class="blog-code-inline">product_id</code> must be a string of 1 to 50 characters, <code class="blog-code-inline">quantity</code> a positive integer, and <code class="blog-code-inline">amount</code> a number within the column's range. In a message-driven system, the entry point is the cheapest place to reject bad input, because it is the only place that can still answer the caller with a 400.</p>

<p class="blog-p">Once the input passes, Node inserts the order as <code class="blog-code-inline">pending</code>, publishes <code class="blog-code-inline">order_created</code> and returns 201 without waiting for the rest of the saga. The client has to ask again later with <code class="blog-code-inline">GET /orders/:id</code>.</p>

<h2 class="blog-h2">4. Redelivery without doing the work twice</h2>

<p class="blog-p">All consumers use <a href="https://www.rabbitmq.com/docs/confirms" target="_blank" rel="noopener">manual acknowledgements</a>. A message is acked after the handler finishes, so if a consumer dies before that, RabbitMQ delivers it again. That is good for not losing work and bad if the work is "charge the customer".</p>

<p class="blog-p">Payment, inventory and shipping each put a <code class="blog-code-inline">UNIQUE</code> constraint on <code class="blog-code-inline">order_id</code> and insert with a no-op on conflict. This is the payment service:</p>

<pre class="blog-pre"><code class="blog-code-block">cursor.execute(
    "INSERT INTO payments (order_id, amount, status) VALUES (%s, %s, %s) "
    "ON DUPLICATE KEY UPDATE status = status",
    (order_id, amount, status),
)
rows_affected = cursor.rowcount</code></pre>

<p class="blog-p">The constraint stops a second row. The row count stops a second event: if it is 0, the handler logs a duplicate, publishes nothing and acks. Without that second check, the database would be safe but the duplicate would still travel down the chain.</p>

<p class="blog-p">There is a portability detail hiding here. The <a href="https://dev.mysql.com/doc/refman/8.4/en/insert-on-duplicate.html" target="_blank" rel="noopener">MySQL manual</a> says this statement reports 1 affected row for a new insert, 2 for a changed row and 0 when an existing row is set to its current values. But if the client connects with the <code class="blog-code-inline">CLIENT_FOUND_ROWS</code> flag, that last case reports 1. None of the three connections here asks for that flag. Turn it on while "tidying up" a connection string and the duplicate check silently stops working. If you copy this pattern, test it with your own driver settings.</p>

<p class="blog-p">The refund uses the same idea in a different shape. It is an <code class="blog-code-inline">UPDATE</code> that sets the status to <code class="blog-code-inline">refunded</code>. The second time, nothing changes, the count is 0, and no second <code class="blog-code-inline">payment_refunded</code> event goes out. Node's final status updates are naturally repeatable, since writing <code class="blog-code-inline">fulfilled</code> twice leaves the order fulfilled.</p>

<h2 class="blog-h2">5. The inventory step needs a real transaction</h2>

<p class="blog-p">Inventory is the one step where a unique key is not enough. It has to read the stock level, decide, record a reservation and decrement the stock. If those are separate statements, two things can go wrong: two consumers can both read the same stock level and oversell, or a failure between the insert and the update can leave a reservation with no matching decrement. The Go service does all of it in one transaction and locks the stock row with <a href="https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html" target="_blank" rel="noopener">SELECT ... FOR UPDATE</a>. Shortened, with error handling removed:</p>

<pre class="blog-pre"><code class="blog-code-block">tx, err := db.Begin()
defer tx.Rollback() // no-op after Commit

err = tx.QueryRow("SELECT available_quantity FROM stock WHERE product_id = ? FOR UPDATE",
    message.ProductID).Scan(&amp;available)

status = "reserved"
if available &lt; message.Quantity {
    status = "released"
}
// INSERT INTO reservations ... ON DUPLICATE KEY UPDATE status = status
// affected == 0: already processed, return without publishing
// status == "reserved": UPDATE stock SET available_quantity = available_quantity - ?
return status, true, tx.Commit()</code></pre>

<p class="blog-p">An unknown product is treated as having zero stock. A refused request is also recorded, with the slightly surprising status <code class="blog-code-inline">released</code>: nothing was ever held, but the row means a redelivered message for that order is recognised as already processed. Only after the commit does the service publish <code class="blog-code-inline">stock_reserved</code> or <code class="blog-code-inline">stock_unavailable</code>.</p>

<p class="blog-p">That "only after the commit" is the right order, and it is also where the biggest gap in the design sits.</p>

<h2 class="blog-h2">6. The gap: commit, then publish</h2>

<p class="blog-p">Every service writes to its database and then publishes to RabbitMQ. Those are two systems, and nothing makes the pair atomic. Walk through the payment service:</p>

<ol class="blog-ol">
<li class="blog-li">It receives <code class="blog-code-inline">order_created</code> and commits the payment row.</li>
<li class="blog-li">The process dies before it publishes <code class="blog-code-inline">payment_completed</code>, and so before it acks.</li>
<li class="blog-li">RabbitMQ redelivers <code class="blog-code-inline">order_created</code>.</li>
<li class="blog-li">The insert hits the unique key, the row count is 0, and the handler decides this is a duplicate.</li>
<li class="blog-li">It acks without publishing. Inventory never hears about the order, which stays <code class="blog-code-inline">pending</code>.</li>
</ol>

<p class="blog-p">The very check that prevents a double charge also swallows the missing event. Idempotent consumers protect against <em class="blog-em">duplicates</em>; they do nothing against <em class="blog-em">loss</em>. These are two different problems, and it is easy to solve the first and assume both are handled.</p>

<p class="blog-p">The standard fix is a <a href="https://microservices.io/patterns/data/transactional-outbox.html" target="_blank" rel="noopener">transactional outbox</a>: in the same local transaction as the business row, insert the outgoing event into an outbox table, and let a separate relay publish it and mark it as sent. The relay may send an event more than once, which is exactly why the idempotent consumers are still needed. The project does not implement this.</p>

<p class="blog-p">The same gap exists at the front door. If Node inserts an order and then fails to publish, the caller gets an error but the <code class="blog-code-inline">pending</code> row remains. And because <code class="blog-code-inline">POST /orders</code> takes no idempotency key, a client that retries simply creates another order.</p>

<h2 class="blog-h2">7. Durable queues are not a delivery guarantee</h2>

<p class="blog-p">The queues are declared durable and messages are published as persistent. The point is that queued messages should survive a broker restart; a durable queue alone does not make its messages persistent, so you need both. Every service that declares a queue also has to declare it with matching settings. RabbitMQ rejects a redeclaration with different properties with <code class="blog-code-inline">PRECONDITION_FAILED</code>, so if you ran an earlier, non-durable version of the project, the README tells you to delete the old queues.</p>

<p class="blog-p">Durability still leaves holes:</p>

<ul class="blog-ul">
<li class="blog-li"><strong class="blog-strong">No publisher confirms.</strong> A service does not wait for the broker to confirm that it took responsibility for a message. See RabbitMQ's page on <a href="https://www.rabbitmq.com/docs/confirms" target="_blank" rel="noopener">acknowledgements and confirms</a>.</li>
<li class="blog-li"><strong class="blog-strong">Failed handlers drop the message.</strong> On an error, consumers nack without requeueing, and the project configures no <a href="https://www.rabbitmq.com/docs/dlx" target="_blank" rel="noopener">dead-letter exchange</a>. On queues set up as this code declares them, with no broker policy adding one, the message is discarded. This avoids an endless redelivery loop for a poison message, but a short database outage is treated the same way as a malformed payload.</li>
<li class="blog-li"><strong class="blog-strong">No prefetch limit.</strong> No consumer sets a <a href="https://www.rabbitmq.com/docs/consumer-prefetch" target="_blank" rel="noopener">prefetch count</a>, so unless the broker is configured with a default, nothing caps how many unacknowledged messages it may push to a consumer.</li>
<li class="blog-li"><strong class="blog-strong">No reconnect logic.</strong> The README says to restart all services after RabbitMQ restarts. The Node API can keep running without a broker connection, in which case new orders return 500 but still leave a <code class="blog-code-inline">pending</code> row. The PHP consumer also holds one long-lived MySQL connection and needs a restart if MySQL closes it.</li>
</ul>

<h2 class="blog-h2">8. Only one thing gets compensated</h2>

<p class="blog-p">Compensation is the part of a saga that replaces rollback, and here there is exactly one compensating action: unavailable stock triggers a refund. A declined payment needs no undo, because nothing happened before it.</p>

<p class="blog-p">Shipping has no failure event. If the PHP service cannot create the shipment, the message is dropped, the payment stays completed, the stock stays reserved and the order stays <code class="blog-code-inline">pending</code>. Nothing releases a successful reservation. There are also no timeouts, so no component notices that an order has been pending too long. A more complete version would publish a <code class="blog-code-inline">shipment_failed</code> event that makes inventory release the stock and payment refund, plus a sweeper for orders that stop moving. In a choreographed saga, every new failure mode means deciding which services must react to it, and nothing in the system tells you when you have forgotten one.</p>

<h2 class="blog-h2">9. Making the invisible visible</h2>

<p class="blog-p">Choreography is hard to follow while it runs, because the story of one order is split across four sets of logs. To show it in one place, each publish of a saga event is followed by a small audit message to <code class="blog-code-inline">q.saga_events</code> that names the order, the event, the queue and the source service. Node consumes it, works out the destination service from the queue name, stores a row in <code class="blog-code-inline">saga_events</code> and serves it at <code class="blog-code-inline">GET /orders/:id/events</code>. In the web UI you can expand an order to see its timeline; while the order is pending, the UI polls once a second.</p>

<p class="blog-p">The events are sorted by <code class="blog-code-inline">occurred_at</code>, set by the publishing service with millisecond precision in the database, with the row id as a tie-breaker. Insertion order is not reliable here, because audit messages from different services can reach Node in a different order from the one in which things happened.</p>

<p class="blog-p">It is worth being clear about what this timeline is. It is for display only; the saga does not depend on it. The audit message is a second, separate publish, so it can go missing even when the saga event went through, and a redelivered audit message can be recorded twice. Its timestamp is taken after the saga event has already been sent, by the clock of whichever service sent it, so treat the order as a helpful view and not as proof of causality. It is not an event store.</p>

<h2 class="blog-h2">10. What I would not copy into production</h2>

<p class="blog-p">Besides the messaging gaps above, the setup is for a local machine only. Connection settings, including default credentials, are hardcoded. The API has no authentication. The repository has no automated tests. There is no product catalogue or price check, and no payment provider. Do not expose it to a network you do not control. The README has a <a href="https://github.com/jmrashed/smallest-microservice/blob/d8aa2672b945e55289e8332b8ecb2766f208480f/README.md#known-limitations" target="_blank" rel="noopener">known limitations</a> section that covers most of these points.</p>

<p class="blog-p">To read or run it, you need RabbitMQ, MySQL, Node.js, Python 3, Go and PHP with Composer; the README lists the versions, extensions, schema files and start order. It is released under the MIT License. A good reading order is the Node service, then Python, Go and PHP, following one queue at a time.</p>

<h2 class="blog-h2">What I would take from this</h2>

<ul class="blog-ul">
<li class="blog-li"><strong class="blog-strong">Idempotency and delivery are separate problems.</strong> A unique key handles the message that arrives twice. It does not help with the message that was never sent.</li>
<li class="blog-li"><strong class="blog-strong">Use a local transaction wherever you still can.</strong> A saga is for crossing service boundaries. Inside one service, the stock check and the decrement belong in one transaction.</li>
<li class="blog-li"><strong class="blog-strong">Validate before the first commit.</strong> Once an event is in flight, there is no caller left to send an error to.</li>
<li class="blog-li"><strong class="blog-strong">List the failure paths, not only the happy path.</strong> For each step, ask what undoes the earlier ones, and what happens if nothing ever answers.</li>
<li class="blog-li"><strong class="blog-strong">State the limits in the repository.</strong> A small demo is more useful when a reader knows which parts are safe to copy.</li>
</ul>
